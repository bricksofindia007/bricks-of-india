## Part C — Social gap root cause

[GH-API] + [RUN-LOG]. Sampled Jul 3, Jul 4, Jun 22, Jun 29 (requested) plus Jun 28 (a claimed-posted day, fetched for contrast).

**Verbatim outcome, identical shape, all four "gap" days:**
```
[scraper*** posted_sets: 26 set(s)          <- (varies by day)
[scraper*** 21 unposted candidates          <- (varies by day)
[scraper*** Skipping <id> -- only 1 gallery images (need 10)
   ...(repeated for every candidate)...
[scraper*** No candidates met the gallery image requirement.
```
Jul 3 (run 28652262957), Jul 4 (run 28701384463), Jun 22 (run 27952839817), Jun 29 (run 28368861786) — **all four** end on that exact line. The GH Actions job exits success every time (this is a deliberate no-op, not a crash) — no post happens because no candidate clears the ≥10-gallery-image bar.

**Contrast — Jun 28 (run 28318178087), a day that did post:**
```
[scraper*** Gallery (43014): 15 images via Brickset API
[scraper*** Selected: 43014-1 - Scuderia Ferrari HP Charles Leclerc Helmet (886 parts, 15 gallery images, availability="")
[db*** Marked 43014-1 as posted. Row ID: 24
[pipeline*** Done. 43014-1 posted successfully.
```
One candidate that day happened to have 15 gallery images (via the Brickset API), cleared the threshold, got selected and posted.

**[DB-QUERY] `posted_sets` per day, last 35 days** confirms this is systemic, not sample bias:
```
05-31:1  06-02:1  06-03:1  06-04:1  06-05:2  06-07:1  06-10:1  06-13:1
06-14:1  06-15:1  06-16:1  06-18:1  06-19:1  06-20:1  06-27:1  06-28:1

Whether that minimum is *correctly* strict (worth asking Abhinav — see OPERATOR-CONFIRM) is a separate, legitimate product question from "is the pipeline broken," which this evidence answers: no.

**Root cause, confirmed two distinct ways, not inferred from the symptom alone:**
1. **[REPO-GREP] Source-level hardcoding** — 16 index pages + `about/page.tsx` + 6 `lab/*` subpages hardcode `| Bricks of India` (or `Bricks of India Lab`) directly in their own `metadata.title` string, e.g. `src/app/deals/page.tsx:12: title: 'Best LEGO Deals in India Right Now | Bricks of India'`. Root layout's `title.template` is `"%s | Bricks of India"` — Next.js appends the suffix a second time on top.
2. **[REPO-GREP] + [DB-QUERY] Data-level duplication** — `blog/[slug]`, `opinion/[slug]`, `guides/[slug]`, `themes/[theme]` correctly use `title: article.seo_title || \`${title} | Bricks of India\`` (template fallback only). But **some stored `seo_title` values already have the suffix baked into the database column itself**: `SELECT count(*) FROM blog_posts WHERE seo_title ILIKE '%bricks of india%'` → **19 rows**; `news_articles` → **20 rows**; `reviews` → **2 rows** (41 content rows total). For these specific rows, the page component is doing nothing wrong — it correctly uses the real stored `seo_title` — but that stored value already carries the suffix, so the layout template still doubles it. Confirmed with a real pair: `best-lego-gifts-kids-india-2026`'s `seo_title` ends in `"...| Bricks of India"` (duplicates); `lego-collections-sharing-with-kids-or-keeping-it-separate`'s `seo_title` does not (clean).

**[LIVE-FETCH] /news freshness vs. DB max:** initial DB max was `2026-07-02 19:03:12`; the live `/news` page's first-listed article at fetch time was "LEGO Lamborghini Revuelto & Huracán STO" — re-querying `news_articles ORDER BY published_at DESC` at that exact moment returned the same title at `2026-07-04 19:35:32` (the mid-audit publish event from Part B). **Match confirmed** — the live page's newest visible article is the DB's actual newest row at every point checked; no caching/staleness gap found.
